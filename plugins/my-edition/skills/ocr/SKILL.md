# 取り込みと誤読チェック

指定された範囲を文字起こしし、誤読を潰し、台帳を更新する。
**ここでの唯一の目的は忠実な転写。**解釈・整形・補完は一切しない。

着手前に `${CLAUDE_PLUGIN_ROOT}/shared/state-format.md` と
`${CLAUDE_PLUGIN_ROOT}/shared/ledger-format.md` を読む。

## 手順1 — 対象を決める

`state.json` を読み、`status: pending` の最初の投入単位を対象にする。
読者が章や節を指定したときはそれに従う。

投入単位は、**画像から起こすときは12ページ前後**。ただし節の切れ目を優先し、12ページは目安。
導出の途中で分断してはいけない。

12ページという数字の根拠は**画像にある。**一度に多くの画像を渡すほど読み落としが増え、
利用上限の消費もここに集中する（手順5）。ページ数はその歯止めである。

**本文データを持ち込んだ場合は、ページ数で切らない。**画像を渡していないので、この歯止めは要らない。
節の切れ目で切り、**1章まるごとを1単位にしてよい**。
それでも章より大きくしないのは、読者が早く手に取れるようにするためである（`build` の手順5）。

## 手順2 — 文字起こし

`references/ocr-prompt.md` のプロンプトを使う。

**モデルは Sonnet 相当を使う。より強い推論モデルを使ってはいけない。**
理由は2つある。

1. 転写は推論ではない。よく推論するモデルは「ここはこう書いてあるはずだ」と**原文を黙って直す**。
   実測で、推論の強いモデルが原文にないプライム記号を補った例が確認されている。
   物理的には正しい補完だったが、それゆえに危険だった——読者は「本にそう書いてある」と信じる
2. 画像入力はこの工程で最もトークンを食う。ここで利用上限を使い切ると、肝心の行間埋めに回らない

プロンプトに「推測で補完しない」と書いても補完は起きる。
**忠実性は指示ではなく検証で担保する**（次の手順）。

出力は `.my-edition/text/<unit-id>.md` に保存する。冒頭に出典コメントを必ず入れる。

```markdown
<!-- source: page_108.jpg / printed page 97 -->
```

## 手順3 — 2段ふるい

1回で完璧にやろうとしない。**粗いふるいと細かいふるいを分ける。**

### 安いふるい（テキストのみ・Sonnet）

`references/sieve-prompt.md` を使い、文字起こしの結果だけを読ませて
「文脈的に破綻している箇所」を挙げさせる。画像は渡さない。

ここは**引っかけすぎてよい工程**である。誤検出しても次段で潰れるだけで、コストは数ページ分。
つまり再現率だけ高ければよく、精度は低くていい。だから安いモデルで足りる。

検出できるのは主に内部矛盾である。

- 総和や積分の添字が、前後と対応していない
- 式番号が飛んでいる、重複している
- 直前の式から論理的に繋がらない変形
- 記号の使い方が台帳と食い違う
- 次元・単位が合わない

### 高いふるい（画像に戻る・強い推論モデル）

引っかかった箇所**だけ**、該当ページの画像に戻って読み直す。ここは難所だけなので量が少なく、
強いモデルを使ってよい。

全ページの画像を強いモデルに渡せばコストが跳ね上がり、テキストだけで済ませれば誤読が残る。
**疑わしい箇所を特定してから、そこだけ精読する**ことで両方を回避している。

## 手順4 — 修正と台帳の更新

確定した誤読を `text/<unit-id>.md` に反映する。
判断がつかない箇所は勝手に決めず、読者に該当ページを示して確認を求める。

そのうえで、登場した式と記号を `ledger.md` に追記する。書式は共有仕様に従う。
**`tex` は原文どおり。物理的におかしくても直さない。**直すのは `fill` の仕事。

`state.json` の当該単位を `checked` に、`ledgerCoverage` を更新する。

## 手順5 — 上限を見張る

`usage.unitsThisSession` を増やす。**3まとまりに近づいたら読者に伝える。**

> このセッションで2まとまり進みました。あと1つで利用上限に当たる見込みです。ここで区切りますか？

さらに、章をいくつか終えて**週の利用上限に近づいている**とき、初めて次を案内する。

> 1冊を通してやると、この構成では2週間前後かかります。
> 文字起こしだけを外部のOCR（Gemini API など）に移すと2〜3日に縮みます。設定は10分ほどです。

**先回りして勧めない。**読者が実際に上限の痛みを感じた直後に出す。
苦行を先に置くと、価値を体験する前に離脱する。

## やってはいけないこと

- 原文の記法の粗さを直す（それは行間であり、`fill` の層で明示して直す）
- 読み取れない箇所を推測で埋める（`[判読不能]` と書いて読者に確認する）
- 式番号を振り直す、通し番号に整える
- 本文を要約する、言い換える
