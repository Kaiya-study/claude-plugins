# 写真から行間を埋める

**準備を一切要求しない。**写真を受け取ったら読み、埋め、足りなければ追加を頼み、
最後に読めるHTMLにまとめて渡す。ここまでが1回分の仕事である。

目次も、較正も、状態ファイルも要らない。これは本づくりの縮小版ではなく、
**独立した使い方**である。「今日この数ページが読めない」を解決する。

## 手順1 — 受け取る

写真1枚から始める。枚数の上限は設けない。会話の中で増えていく前提で扱う。

画像がない状態で呼ばれたら、撮って送るよう頼む。**数式の添字が潰れない程度の解像度**が要ることを
一言添える。斜めや影は問題ないが、小さすぎる文字は読めない。

10枚を超えるようなら、「まとまった量なら通しでやるほうが向いています」と伝えて `make` を案内する。

## 手順2 — どの資料のものか確かめる

写真は溜まっていく。**資料ごとに置き場所を分けないと、混ざって使えなくなる。**
別の日に撮った続きも、行き場がなくなる。

**白紙で「どの資料ですか」と聞かない。**軽さという取り柄が消える。
**中身から推測して、確認を求める。**

> 相対性理論の教科書のようです。`相対論` というフォルダにまとめますか？

既に置き場所がある場合（下記の探索で見つかる場合）は、候補を出す。

> 前に `相対論` で作ったものがあります。その続きですか？

会話の流れで既に分かっているときは、**聞かない**。

### 置き場所

利用者にパスを意識させない。ファイルを書ける環境なら、次の形で作る。

**根はホームフォルダに固定する。**Windows は `%USERPROFILE%\my-textbooks\`、
macOS / Linux は `~/my-textbooks/`。**開いているフォルダの下に作らない。**
どのフォルダで呼ばれても同じ場所を使うためで、そうしないと理解状況も資料も散る。

```
~/my-textbooks/
├── profile.md          ← 理解状況。資料をまたいで1つだけ
├── assets/
│   └── tex-svg.js      ← MathJax。初回だけ取得し、資料をまたいで使い回す
└── <資料名>/           ← 資料ごと。置き場所は暫定（下記）
    ├── photos/         ← 送られた写真（原本）
    ├── parts/          ← 自分が書くのはここだけ
    │   ├── title.txt   ← 資料名を1行
    │   ├── rail.html   ← サイドバー
    │   └── body.html   ← 本文と補完
    ├── ledger.md       ← 式・記号・図の台帳
    └── <資料名>.html   ← マイ教科書。手順8のコマンドが作る。手で書かない
```

- **`profile.md` と `assets/` の場所は動かさない。**この2つは資料ではなく、
  読む人と機械に属する。一冊まるごとの経路も同じものを使う
- **`<資料名>/` の置き場所は暫定である**（2026-09-12）。いまは同じ根の下に置くが、
  あとで変わりうる。ここのパスを他の文書に焼き付けない

着手前に `~/my-textbooks/` の下を見て、既存の資料フォルダと `profile.md` を把握しておく。

**ファイルを書けない環境（スマートフォンなど）では、この手順ごと飛ばす。**
その場合は従来どおり会話の中だけで完結させ、HTMLをその場で返す。
フォルダがないことを問題として報告しない。

## 手順3 — 転写する

`${CLAUDE_PLUGIN_ROOT}/skills/ocr/references/ocr-prompt.md` に従う。**忠実性の規律は同じ。**

- 原文を直さない。物理的におかしく見えても、書いてあるとおりに読む
- 読み取れない箇所は `[判読不能]` とし、推測で埋めない

枚数が少ないので、2段ふるいは軽量版でよい。転写を一度読み返し、**内部矛盾**
（添字の不一致、式番号の飛び、前の行と繋がらない変形）だけ点検する。引っかかったら画像で読み直す。

## 手順4 — 聞くことを、写真から決める

**質問は1つだけにする。**手順2と合わせても2問まで。ここで5問聞くと軽さが消える。

**白紙で「どのくらい説明しましょうか」と聞かない。**当てにならない自己評価しか返らない。
**いま転写したページに実際に出てくる操作を名指しして、説明なしで読めるかどうかだけを聞く。**

転写した中から、**そのページの山になっている操作**を1つ選ぶ。
そこが読めるかどうかで、このページの行間の広さが決まる、という箇所である。

> このページは `∂²/∂t² − c²∇²` を別の座標に書き直すところが山です。
> この書き換えが導出なしで出てきたら、そのまま読めますか。

聞き方の規則は `${CLAUDE_PLUGIN_ROOT}/skills/setup/references/profile-questions.md` の
「質問の作り方」に従う。**式は普通の文字で書き、1行に収める。**

答えは三択（既知／怪しい／未習）として受ける。既知なら行間を作らず、怪しいなら通常の粒度、
未習なら定義から書く。

- 答えが返らなければ**未習と仮定し、そう仮定したことを明示して**進む。**待たない**
- **聞くのは、その資料の初回だけ。**`profile.md` があれば、写真が何枚増えても聞かない
- 一度聞いたら、その会話の中では同じことを二度聞かない

文章が主体で、名指しできる操作が見当たらないページもある。そのときだけ、従来の形で聞く。

> どのくらいまで説明しましょうか。
> ①式変形だけ追えれば十分 ②定理や条件の根拠も知りたい ③定義から丁寧に

### 答えを書き残す

**聞きっぱなしにしない。**残さないと、次に写真が届いたときに同じことをまた聞くことになる。

`~/my-textbooks/profile.md` に、`profile-questions.md` の書式で1行足す。
**資料ごとに作らない。**この1つを資料をまたいで使う。

```markdown
| 座標変換（∇² の書き換え） | 怪しい |
```

仮定のまま進んだ項目には印を残す（`未習（仮定）`）。あとで挙動を見て直せる。

**2回目以降は、こちらから聞かない。**写真が増えても、その写真が別の操作を含んでいても、
`profile.md` をそのまま使う。**聞き直すたびに、写真を貼るだけという取り柄が削れる。**

粒度は、こちらが聞き直すのではなく**利用者の質問で動かす**
（下の「補完について質問されたら、記録する」）。
初回の1問で当たりを付け、あとは読んでいて引っかかった箇所から直していく。

**ファイルを書けない環境では、この節ごと飛ばす。**会話の中でだけ使い、
フォルダがないことを問題として報告しない。

## 手順5 — 埋める

`${CLAUDE_PLUGIN_ROOT}/skills/fill/SKILL.md` の探索と充填、および
`${CLAUDE_PLUGIN_ROOT}/skills/fill/references/quality-bar.md` の4条件に従う。

プロファイルは `~/my-textbooks/profile.md` にある。**両方の経路が同じものを読む。**
手順4で得た答えと、そこに「粒度の調整」があればそれに従って粒度を決める。

1ステップ1操作、根拠の明示、飛躍の自己申告、検算の手がかり。
**目的は「正しい答えを与えること」ではなく、読者が自分で検証できる形にすること。**

## 手順6 — 足りなければ、こちらから頼む

**これがこの使い方の要である。**写真の範囲しか見えていないので、外に出ている参照が必ず起こる。
**推測で埋めてはいけない。**黙って「おそらくこういう式でしょう」と補うのが最悪の失敗になる。

必要なものが欠けていたら、**具体的に**頼む。

> この変形は (1.7) を使っていますが、写真にはありません。数ページ戻ったあたりだと思います。
> そこも撮って送っていただけますか。

頼む対象は主に次の3つ。

- **参照されている式** — 「(1.7) より」の (1.7) が写っていない
- **記号の定義** — この本での `φ` が何かが写っていない。巻末の記号表でもよい
- **図** — 本文が図を指しているが写っていない

台帳（`ledger.md`）があれば、**何が既に手元にあるかがそこで分かる**。毎回それを見てから頼む。

追加の写真が届いたら、**それも含めて全体を組み直す**。前に埋めた箇所も、
新しい情報で正確になるなら書き直す。

写真が手に入らないと言われたら、**そのまま進めてよい。**ただし
「(1.7) が不明なので、ここは一般的な形を仮定しています」と明示する。仮定を隠さない。

## 手順7 — 台帳を更新する

書式は `${CLAUDE_PLUGIN_ROOT}/shared/ledger-format.md` に従う。第1段では軽い形でよいが、
**式・記号・図と、末尾の `## 未解決` は必ず書く**。次に写真が届いたときの判断材料になる。

原著が式に番号を振っていない本では、この版で通し番号を振る（`markup.md` の規則に従う）。

## 手順8 — HTMLにまとめる

**聞かれる前に作る。これが成果物である。**

`${CLAUDE_PLUGIN_ROOT}/skills/build/references/markup.md` に従って断片を書く。
**一冊まるごとの経路と同じテンプレート・同じ構造を使う。**独自の見た目を作らない。

- 本文が主役。補完は式に付随させ、「途中式をひらく」で開く
- 式番号のリンク、逆引き、原著モード、質問チップはテンプレートが持っている
- 左のプロファイル欄には、`profile.md` の内容（手順4で確かめた操作と状態）を入れる
- 目次には、いま写真がある範囲だけを並べる

### 書くのは断片だけ

**MathJax 本体を自分で書き出してはいけない。**出力の約95%は MathJax で、
自分が作っているのは残りの3%にすぎない。写真が増えるたびに2MB を書き直すと、
待ち時間がそこで決まってしまう。

自分が書くのは `parts/title.txt`・`parts/rail.html`・`parts/body.html` の3つ。
**写真が増えるたびに、`body.html` と `rail.html` を書き直す。**

### 連結はコマンドに任せる

MathJax を `~/my-textbooks/assets/tex-svg.js` に取得する（無ければ一度だけ。
`${CLAUDE_PLUGIN_ROOT}/skills/build/SKILL.md` の「MathJax の取得」と同じ。3.2.2 に固定）。

macOS / Linux:

```
sh "${CLAUDE_PLUGIN_ROOT}/skills/build/assets/assemble.sh" \
   "${CLAUDE_PLUGIN_ROOT}/skills/build/assets/template.html" \
   "$HOME/my-textbooks/<資料名>/parts/title.txt" "$HOME/my-textbooks/<資料名>/parts/rail.html" \
   "$HOME/my-textbooks/assets/tex-svg.js" "$HOME/my-textbooks/<資料名>/<資料名>.html" \
   "$HOME/my-textbooks/<資料名>/parts/body.html"
```

Windows:

```
powershell -NoProfile -ExecutionPolicy Bypass -File "${CLAUDE_PLUGIN_ROOT}/skills/build/assets/assemble.ps1" "${CLAUDE_PLUGIN_ROOT}/skills/build/assets/template.html" "$env:USERPROFILE\my-textbooks\<資料名>\parts\title.txt" "$env:USERPROFILE\my-textbooks\<資料名>\parts\rail.html" "$env:USERPROFILE\my-textbooks\assets\tex-svg.js" "$env:USERPROFILE\my-textbooks\<資料名>\<資料名>.html" "$env:USERPROFILE\my-textbooks\<資料名>\parts\body.html"
```

- **`-ExecutionPolicy Bypass` を省かない。**既定の設定では `.ps1` の実行が拒否される
- 取得できなかったときは、MathJax の位置に `-` を渡す（軽量版。ネットがないと数式が出ない）。
  **組版そのものは止めない**
- **ファイルを書けない環境では、この節ごと飛ばす。**会話の中でHTMLを返して終わる

チャットにも、埋めた内容の要点は返す。ただし全文を書き写さない——
**読むのはHTMLのほう**であり、チャットは「何が埋まったか」の一覧と、
判断を仰ぎたいこと（判読不能、追加で欲しい写真）に絞る。

## 補完について質問されたら、記録する

**利用者の質問は、行間の粒度に対する唯一の証拠である。**答えて終わりにしない。

生成したHTMLの「この説明について聞く」から来た質問も、口頭での質問も、同じ扱い。

- **詳しく質問された** → その書き方ではまだ行間が広い。同じ種類を細かく割る
- **「ここまで丁寧でなくてよい」と言われた** → そこは行間ではなかった。同じ種類を広げる

答えたあとに、`~/my-textbooks/profile.md` の「粒度の調整」へ**きっかけと資料名を一緒に**書く
（書式は `${CLAUDE_PLUGIN_ROOT}/skills/setup/references/profile-questions.md` の「更新」）。
範囲が判断できないときは聞く。「同じような式変形も、すべて細かくしますか」

**質問が来ないことを理由に、行間を広げてはいけない。**
沈黙は「分かっている」ではなく、「まだ読んでいない」かもしれない。
粗くしてよいのは、利用者が明示的にそう言ったときだけ。

## 手順9 — 重くなってきたら、一度だけ次を勧める

**先回りして勧めない。**写真を貼るだけで済むのがこの使い方の価値なので、
最初から「PCでやったほうがいい」と言うと、その価値を自分で壊すことになる。

**実際に重くなった兆候が出たときだけ、一度言う。**同じ会話で二度言わない。

| 兆候 | 何が起きているか | 勧める先 |
|---|---|---|
| 資料フォルダが3つ以上になった | 毎回「どの資料か」の確認が要る。整理の限界 | PCでの作業 |
| 1つの資料の写真が10枚を超えた | 手で撮るのが苦行になっている | `make`（通し） |
| 同じ資料で3回目以降のセッション | 継続的な作業になっている | PCでの作業 |
| **同じ資料で追加写真を3回以上頼んだ** | 断片的に撮る限界。前後が繋がっていない | まとめて取り込む |

最後の兆候がいちばん鋭い。こちらが何度も「前のページも」と頼んでいるということは、
**写真という入力が材料に負けている**。

言い方は、**利用者がいま感じている面倒を名指しする**。「上級者向け」「本格的にやるなら」
という出し方をしない。それは押し売りに聞こえる。

> 資料が3つになりました。PCでスキャンをフォルダにまとめておくと、
> どれの続きかを聞かずに済みますし、章単位でまとめて作れます。

> このページの前後を3回お願いしています。1章分をまとめて取り込んだほうが早いかもしれません。

断られたら、そのまま続ける。**それきりにする。**

資料フォルダを作ってあれば、**そのまま `make` に引き継げる**。同じ場所に `.my-edition/` を
足すだけで通しの作業に移れる（写真も台帳も引き継がれる）ので、乗り換えで失うものはない。
そう伝えてよい。

兆候が出ていないときは、最後に**一行だけ**添えて終わる。

> 同じ本を続けるなら、写真を足していけばこのファイルが育ちます。

## 態度

- **速さが価値。**確認や前置きを増やさない。写真が来たらすぐ読む
- 質問は多くて2つ（置き場所と、そのページの山になっている操作）。
  しかも**写真を読んだうえで、具体的に名指しして聞く**
- 工程名（OCR、行間埋め、台帳）を出さない
- 分からないことは分からないと言う。**判読不能と、写真の外への参照は必ず明示する**
